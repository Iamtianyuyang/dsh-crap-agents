# 规格阶段（Specifier）

Bob 大叔：**验收测试就是需求本身**。人类会读你写的场景来判断"这是不是我要的"，
所以场景要用业务语言写，不能出现函数名、类名、文件名。

## 步骤

1. 按 gauntlet-core 第 1、2 节读任务、确认在工作分支上。
2. **先读项目档案 `.gauntlet/GAUNTLET.md`**（第 0 阶段摸底写的）：项目是什么、代码地图、怎么运行交付物、现有约定。
   `.gauntlet/` 安装、`.gauntlet/gauntlet.config.json`、架构规则、棘轮基线都由摸底阶段负责，你不改它们。
   发现它们和需求冲突（例如需求要求的新目录不在 `sources` 里）：NEED-HUMAN，说明冲突在哪；Leader 会安排回到第 0 阶段摸底重来。
3. 写 `.gauntlet/qa/constraints.json`：**需求原文里每一条明确要求都是一条约束**（见下文「需求约束」）。
4. 判断任务类型。**重构、合并、移植、优化**这类"行为不应改变"的任务：在 `.gauntlet/gauntlet.config.json` 设
   `"requireEquivalence": true`，并在 QA 文档里写清楚等价性对比计划（见下文「与原程序等价」）。
5. 写 `.gauntlet/features/<主题>.feature`（一个功能一个文件，文件名用英文小写+下划线）。
6. 写 `.gauntlet/qa/<主题>.qa.md`（QA 步骤，见模板），每条检查标注它证实哪条约束。
7. 运行 `node .gauntlet/gauntlet.mjs gate --profile specifier`，直到 PASS
   （这一阶段允许步骤"未定义"，但语法必须正确、不能有歧义步骤）。
8. 提交、推送、按 gauntlet-core 第 6 节收尾。

## 需求约束（.gauntlet/qa/constraints.json）

把需求里所有"必须/只能/不许/在哪里/用什么"类的要求逐条抄出来，**用需求原话**，不要合并、不要省略、不要自己加限定：

```json
[
  { "id": "C1", "text": "在服务器 172.19.133.164、163、162 上编码和测试", "verify": "QA 在三台服务器上分别构建并跑全部测试，记录主机名" },
  { "id": "C2", "text": "只能在 /public/tianyuyang/code/IFDTD3D-Unified 中写东西", "verify": "运行前后对比仓库外目录（含 /tmp、~/.cache）没有新文件" },
  { "id": "C3", "text": "中间文件都放在 tmp 文件夹中", "verify": "构建/输出/日志目录都在 tmp/ 下；仓库根目录除源码外无新增文件" }
]
```

- 某条约束当前做不到（比如某台服务器 SSH 不通）：照样写进去，并在结果里用 NEED-HUMAN 指出——由人决定是修环境还是改需求。
- 闸门 `constraints` 会检查每条约束都有通过的 QA 检查证实；没有证实的约束 = 闸门失败。

## 与原程序等价（重构 / 合并类任务）

"把 A 和 B 合成一个程序""重构""优化性能"——验证标准是：**新程序在同样的输入下产生和原程序一样的输出**。
只比较新程序的两个后端彼此一致是不够的（它们可能以同样的方式错）。在 QA 文档里写清：

- 基线：哪个 commit 的原程序（一般是任务开始时的默认分支），在工作目录（如 `.gauntlet/tmp/baseline/`）里构建；
- 用例矩阵：每个求解方法 × 每个后端 × 至少两种网格规模；
- 对比的输出：每一种输出文件（快照、地震记录……）都要比，写清数据类型、文件头字节数、每帧元素数；
- 容差：能逐位一致的用 `--exact`；浮点重排导致不能逐位一致的，给出容差和理由。

## 写场景的规则

- 中英文关键字都支持：`功能/Feature`、`背景/Background`、`场景/Scenario`、`场景大纲/Scenario Outline`、
  `例子/Examples`、`假如/Given`、`当/When`、`那么/Then`、`而且/And`、`但是/But`。
- 每个场景只验证**一个**行为；`当` 只出现一次。
- 用 `场景大纲 + 例子` 覆盖边界值：最小值、最大值、刚好越界、空输入、非法输入。
- 每条需求规则至少一个正例 + 一个反例（错误处理也是需求）。
- 参数写法要稳定：数字直接写，字符串用双引号 `"..."`（cmake 适配器的步骤占位见其技能）。
- 场景名唯一、稳定：commands 适配器靠测试名包含场景名来对应验收测试。
- 多行输出用文档字符串：
  ```gherkin
  那么 输出应为:
    """
    第一行
    第二行
    """
  ```
- 复用同样措辞的步骤（"我执行转换"不要在别处写成"执行一次转换"）。

## 需求有歧义时

不要猜。把问题列出来（每个问题给出 A/B 选项和你的推荐），按 gauntlet-core 第 6 节的 `NEED-HUMAN` 收尾。
已经确定的部分照常写进 feature 并提交。

## QA 步骤模板（.gauntlet/qa/<主题>.qa.md）

```markdown
# QA：<功能名>

前置：如何构建、真实产物在哪、怎么运行（见适配器技能「5 QA」）

| # | 检查项 | 操作（真实命令或界面操作） | 期望结果 | 证实约束 |
|---|---|---|---|---|
| 1 | 正常转换 | `roman 2026` | 输出 `MMXXVI`，退出码 0 | C1 |
| 2 | 非法输入 | `roman IIII` | stderr 含 `not a valid`，退出码 2 | C2 |
```

每条约束至少要有一条检查证实它。

QA 步骤面向**真实产物**（可执行文件、库的示例程序、GUI），和验收场景互补：
验收场景在进程内验证行为，QA 证明交付物真的能用。

## 架构草稿

按"深模块、窄接口"（Ousterhout）划分：核心领域逻辑一个模块，不依赖任何 IO；
应用/命令行/界面层依赖领域层；第三方适配层单独一个模块。依赖方向只能指向更稳定的模块。
**每个产品代码目录都必须属于某个模块。**

规则写在哪里、什么格式由适配器决定：cmake-clang 写 `.gauntlet/architecture.json`；commands 写进 `commands.arch`
所用工具的规则文件。已经存在的架构规则你**不能**修改；如果需求必须改架构，用 `NEED-HUMAN` 提出来。
